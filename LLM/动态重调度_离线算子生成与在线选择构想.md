# 动态重调度：LLM离线算子生成与在线选择构想

## 一句话定位

LLM不直接参与实时排程，而是在离线阶段设计并验证一组可执行、互补的邻域算子；动态事件发生后，轻量选择器依据当前重调度状态选择算子，调用既有解码器完成快速评价和搜索。

## 推荐总体结构

```text
离线慢循环
问题知识 + 人工算子N1–N6 + 历史失败案例
    -> LLM生成候选算子代码
    -> 静态检查与接口检查
    -> 染色体可行性检查
    -> 原动态解码器评价
    -> 多场景统计筛选
    -> 冻结互补算子库 Ω

在线快循环
扰动发生 -> 提取状态特征 -> 选择 Ω 中的算子
    -> 产生邻域解 -> 原解码器评价 -> 接受/拒绝
    -> 更新算子信用值
```

## LLM应当生成什么

第一阶段只允许LLM生成“邻域提案函数”，不能生成或修改解码器、TEC公式、故障规则和约束处理逻辑。统一接口可以抽象为：

```python
candidate = operator(solution, state, rng)
```

输入包括当前染色体、允许使用的状态摘要和受控随机源；输出只能是候选染色体或一组有限编辑动作。可从以下算子族开始：

1. 工序顺序算子：在不破坏工序优先关系的前提下交换、插入或移动关键工序。
2. 机器重分配算子：将瓶颈或受故障影响工序迁移到可选机器。
3. AGV重分配算子：调整运输任务的AGV分配，降低等待、空载移动或充电冲突。
4. 耦合算子：同时修改机器选择和AGV选择，处理“换机器导致运输路径变化”的联动。
5. 恢复算子：优先修改扰动影响区域，减少对原计划的破坏。
6. 能耗算子：针对高空载里程、高待机能耗或高峰功率片段提出局部调整。

## 离线评价不能只看一个加权和

每个候选算子至少记录：

- 可行解产生率；
- 单位解码次数带来的Makespan改善；
- 单位解码次数带来的TEC改善；
- 对Pareto前沿的HV增量或支配贡献；
- 运行时间；
- 不同扰动类型和强度下的稳定性；
- 与现有算子的行为重合度；
- 对原计划的扰动程度。

算子入库应同时满足安全门槛和互补性要求。EoH负责生成单个有效算子，EoH-S思想负责从候选集中选择覆盖不同场景的较小算子集合。

## 在线状态特征

在线选择器不读取完整自然语言，而使用可复现的数值状态：

- 扰动类型：订单取消、机器故障、AGV故障；
- 扰动强度：受影响工序数、剩余工序比例、资源损失比例；
- 时间阶段：扰动发生时刻相对于原计划完工时间的位置；
- 机器状态：平均负载、最大负载、负载方差、瓶颈机器等待；
- AGV状态：利用率、空载比例、排队长度、位置离散度、电量风险；
- Pareto状态：非支配解比例、HV近期变化、种群多样性；
- 搜索状态：连续无改进次数、剩余评价预算、各算子近期成功率。

## 三种在线选择方案

### 方案A：上下文多臂老虎机（推荐首篇小论文）

把每个离线算子视为一个臂，根据当前状态和历史回报选择算子。优点是实现简单、在线开销小、信用分配清楚，能够回答“什么扰动状态下哪个算子有效”。回报可由HV增量、可行性和运行时间组成，但权重必须通过消融实验说明。

### 方案B：保留原Q-learning并扩展动作集

把人工N1–N6和LLM算子共同作为动作，状态继续采用原QNSGA-II定义或经过审慎扩展。优点是与现有baseline衔接自然；风险是如果同时修改状态、动作和奖励，无法判断提升来自LLM算子还是强化学习结构变化。

### 方案C：离线训练的算子评分器

利用离线运行数据训练模型预测每个算子的预期收益，在线选择预测最高者。可能性能较强，但会引入训练集划分、分布外泛化和模型复杂度问题，不适合作为最先实现版本。

## 推荐的最小论文版本

1. 基线保持原QNSGA-II及人工N1–N6不变。
2. 使用EoH生成候选算子，并用EoH-S式互补筛选得到3–6个冻结算子。
3. 在线选择使用上下文多臂老虎机，不在线调用LLM。
4. 三类动态事件分别训练/统计，但使用统一算子接口。
5. 用相同实例、解码器、评价预算、随机种子政策和指标比较。

## 必须设置的对照与消融

- 原QNSGA-II + N1–N6；
- 原QNSGA-II + LLM算子库 + 随机选择；
- 原QNSGA-II + LLM算子库 + 固定概率选择；
- 原QNSGA-II + LLM算子库 + 在线自适应选择；
- 人工算子与LLM算子混合库；
- 单个最佳LLM算子与互补算子集合；
- 去掉状态中的扰动信息或资源拥堵信息。

## 主要风险

1. **可行性风险**：LLM代码可能破坏染色体结构。解决办法是限制编辑原语，并由独立验证器拒绝非法输出。
2. **评价泄漏**：生成阶段与测试阶段使用相同实例会夸大结果。必须按实例规模、扰动类型和随机种子划分生成集、验证集和测试集。
3. **预算不公平**：LLM离线成本不应混入在线算法运行时间，但必须单独报告调用次数、token和生成耗时。
4. **贡献混淆**：同时改变解码器、奖励和算子会失去归因。第一篇论文应冻结解码器及TEC口径。
5. **算子过拟合**：只在单一事件或规模上筛选会造成泛化失败，因此入库标准必须包含跨场景稳定性。

## 当前结论

最可控的创新不是“LLM在线求解重调度”，而是“LLM离线设计互补邻域算子 + 轻量上下文选择器在线组合”。该结构既能利用LLM的代码与策略生成能力，又保持动态调度的实时性、可复现性和基线边界。
