# 12｜机制演进地图

> 版本：V1（基于 `LLM/` 69 篇正文）
>
> 核心抽象：**State / Context → Decision Mechanism → Action / Strategy → Executor → Feedback → Performance**。
>
> 目的：不比较花哨算法名，而是判断“谁在看什么信息、做什么决策、选择什么动作、谁真正执行、反馈如何回流”。

## 重点中的重点

【文献归纳】LLM × Optimization 的真正机制演进，不是简单的“模型越来越大”，而是 LLM 所处的**决策层级**不断变化：

1. 直接输出 solution；
2. 把自然语言转成 model/code，再由 solver 执行；
3. 生成一个可重复运行的 heuristic；
4. 在 evolutionary search 中生成、反思和改进 heuristic；
5. 设计一组 heuristic / operator / solver component；
6. 根据 context 在线选择已有策略；
7. 利用 trajectory、memory、feedback 和预算进行长期高层控制。

这条机制线比“LLM 用在什么应用场景”更能解释领域前沿。

---

# 统一机制坐标

任何论文先还原成五个问题：

| 层 | 必问问题 |
|---|---|
| State / Context | 方法看见了什么？实例特征、当前解、动态事件、搜索阶段、历史效果、预算？ |
| Decision Mechanism | 谁做决策？固定规则、Bandit、RL、Q-learning、LLM、Agent、EC、MCTS？ |
| Action / Strategy | 它选什么？解、heuristic、operator、algorithm、code、模型结构、参数？ |
| Executor | 真正执行搜索的是谁？LLM、EA、local search、solver、simulator？ |
| Feedback | 决策后拿到什么？objective、reward、solver log、critique、trajectory、HV、runtime？ |

---

# M0｜固定 heuristic / 人工算法

```text
问题实例
→ 人工固定规则
→ 固定 heuristic / operator
→ solver / search engine
→ objective value
```

## 特征

- 高度可解释、执行快；
- 依赖领域知识；
- 环境变化后需要人工重新设计。

## 机制瓶颈

**Decision Mechanism 是人。**

后续所有 HH / RL / LLM 路线本质上都在试图自动化这一层。

---

# M1｜Algorithm Selection / Hyper-Heuristic / AOS

```text
instance / search features
→ rule / statistical model / bandit / hyper-heuristic
→ 从有限 LLH / operator pool 选择
→ 原优化器执行
→ performance / reward
```

## 机制升级

第一次把“**选哪个 heuristic/operator**”明确提升为一个独立高层问题。

【原文事实】78 号综述区分 automated design 与 selection/AOS；54 号 MEoH 也回顾 configuration、selection、composition 三类自动设计。

## 增益

- 低层执行器可保持不变；
- 可以根据实例或搜索状态适应。

## 代价

- heuristic pool 仍由人预定义；
- feature / credit assignment 仍需要设计。

---

# M2｜RL / Q-learning Selector

```text
手工或学习得到的 state
→ Q-learning / RL policy
→ heuristic / neighborhood / operator
→ optimizer
→ scalar reward / objective improvement
```

## 机制升级

从“规则选择”变成**根据交互经验学习策略**。

## 优势

- 能建立 state-action-effect 映射；
- 适合重复决策和动态环境。

## 固有限制

【文献归纳】这一类机制通常依赖：

- 状态离散化/feature engineering；
- reward shaping；
- 训练数据和足够交互；
- 分布改变后策略迁移能力不稳定。

这正是当前“LLM selector 是否有价值”的合理比较对象，而不是一个应该被忽略的旧 baseline。

---

# M3｜LLM 直接作为 Solution Optimizer

代表：OPRO（73）、SGE（63）、部分 graph / CO direct solving、STARJOB（36）。

```text
problem description + historical solutions
→ LLM reasoning / prompting
→ complete or partial solution
→ checker / objective evaluator
→ score
```

## OPRO 的关键机制

【原文事实】OPRO 的 meta-prompt 中包含历史 `solution-score pairs`，LLM 根据整个 optimization trajectory 提议新解。

## SGE 的关键机制

LLM 先生成多条 solution trajectory，再 decomposition、execution、feedback、refinement、integration。

## 增益

- 几乎不需要定义传统 update rule；
- 可以利用自然语言和历史模式。

## 机制瓶颈

GraphArena / NLGraph 说明复杂结构与规模上存在可行性、optimality、hallucination 问题。

**结论：LLM 直接承担低层求解并不是最稳的角色分配。**

---

# M4｜LLM Formulator + Classical Solver

代表：NL4Opt（77）、Holy Grail 2.0（74）、OptLLM（60）、OptiMUS（67/59）、ORLM（62）、LLMOPT（51）、OR-LLM-Agent（33）。

```text
natural language problem
→ LLM semantic understanding / formulation / code generation
→ mathematical model / solver code
→ Gurobi / MiniZinc / OR solver
→ execution result / error log / feasibility
→ LLM correction
```

## 机制升级

把 LLM 与传统求解器**按能力分工**：

- LLM：语义理解、结构提取、代码生成；
- solver：精确计算和 feasibility；
- feedback：编译错误、solver result、solution correctness。

## 重要机制原则

【文献归纳】这一分支最稳定的进步来自“**闭环与验证**”，而不是单纯更强模型。

证据：

- Auto Model Generator（76）：compile-error feedback 自动修复；
- Mamo（64）：solver output 作为 modeling correctness 验证；
- OptMATH（42）：solver-based rejection sampling；
- EquivaMap（39）：功能等价性验证；
- OptiMUS-0.3（59）：modular architecture + targeted error correction。

对调度 selector 的启示：LLM 决策也应该被 objective/optimizer feedback 约束，而不是只相信自然语言理由。

---

# M5｜LLM Heuristic Generator / Language Hyper-Heuristic

代表：EoH（69）、ReEvo（68）。

```text
task specification
→ LLM generation
→ heuristic thought + code
→ fixed optimization framework executes heuristic
→ instance-level fitness
→ evolutionary update / reflection
```

## EoH

State/Context：任务描述 + population 中已有 heuristic。

Decision：LLM + EC prompt strategies。

Action：产生新的 thought + executable heuristic code。

Executor：原有 heuristic framework / benchmark evaluator。

Feedback：heuristic fitness。

## ReEvo

在 EoH 型框架上增加：

```text
relative performance
→ reflector LLM
→ short-term / long-term verbal gradients
→ generator LLM
→ improved heuristic
```

## 机制意义

LLM 从“直接输出解”升级为“**设计一个低成本、可重复执行的算法**”。

这是 AHD 路线的关键转折。

---

# M6｜Search-aware AHD：LLM 不只生成，还管理搜索过程

代表：HSEvo（45）、QUBE（44）、MCTS-AHD（43）、Planning of Heuristics（40）、PathWise（05）、DASH（07）、Hercules（26）。

## 共同机制变化

旧机制只看：

```text
heuristic → final fitness
```

新机制开始看：

```text
search trajectory
population diversity
uncertainty
parent lineage
past reflections
runtime / convergence
remaining search opportunity
```

### HSEvo

显式度量 heuristic population diversity，并平衡 exploration / exploitation。

### QUBE

用 quality + uncertainty 控制 parent priority。

### MCTS-AHD

把 heuristic evolution 组织为树，不立即淘汰暂时低性能路径。

### Planning of Heuristics

把 heuristic improvement 形式化为 MDP：heuristic = state，improvement suggestion = action，performance = reward。

### PathWise

强调 stateful trajectory 与 search memory，让 policy agent 做高层 action planning。

### DASH

不只看 endpoint score，而关注 trajectory-aware convergence 和 runtime schedule。

## 机制意义

**反馈从“单个结果”升级为“过程状态”。**

这与当前研究要加入搜索阶段、Pareto 停滞、上一步策略效果、剩余预算高度相关。

---

# M7｜从单 heuristic 到 portfolio / multi-operator / system-level design

代表：EoH-S（18）、E2OC（06）、MEoH（54）、MPaGE（21）、AutoPBO（16）、EvoPlace（30）、AutoRNet（50）。

## 机制变化

```text
一个候选 heuristic
↓
多个互补 heuristic / operator / component
↓
考虑组合关系、trade-off 与系统级行为
```

### EoH-S

输出 complementary heuristic set，而不是 one-size-fits-all heuristic。

### E2OC

显式考虑 operator interdependence 与 co-evolution。

### MEoH / MPaGE

heuristic 自身的设计目标变成多目标，考虑性能、效率、runtime、diversity 等 trade-off。

### AutoPBO / EvoPlace / AutoRNet

LLM 设计范围扩展到多个 solver component、完整 algorithm structure 或工业复杂模块。

## 机制意义

为下一步“**有一个策略库，然后在线决定什么时候用哪一个**”提供了结构前提。

---

# M8｜LLM Contextual Selector：在线从策略库选择

这是当前研究最敏感的一层。

## HeurAgenix（23）

```text
current problem state + remaining decisions
→ LLM / fine-tuned lightweight selector
→ heuristic from heuristic pool
→ problem solver executes
→ updated state
```

【原文事实】它明确属于 selection hyper-heuristic，而不只是 heuristic generation。

## MA-GTS（37）

```text
problem constraints + graph scale
→ agentic algorithm selection
→ algorithm from library
→ code interpreter executes
```

## Wireless Power Control（58）

```text
current environment state
+ experience pool(state, action, reward)
→ LLM in-context decision
→ power level action
→ environment
→ reward
→ append to experience pool
```

## 机制意义

“LLM 根据 context 在线选动作/heuristic”已经是**真实存在的机制类别**。

因此当前研究不能把“LLM selector”三个字本身当 novelty。

---

# M9｜Dynamic Strategic Control：动态环境 + 反思/长期经验

代表：ReflecSched（19）、TPET（09）等。

## ReflecSched

```text
dynamic FJSP observations / simulation horizons
→ hierarchical reflection
→ strategic experience
→ LLM decision module
→ instantaneous scheduling action
```

它说明 LLM 已经进入动态 FJSP，并承担战略分析与即时决策。

## TPET

```text
traffic state + temporal history
→ Structured State Abstraction
→ lightweight evolved policy
→ traffic simulator
→ logs
→ Credit Assignment Feedback
→ LLM evolves policy offline
```

TPET 反而强调：**慢 LLM 不适合高频在线 actor，适合发现快速 policy。**

## 机制争议

这里形成一个真正值得维护的争议节点：

- 路线 A：LLM 在线决策，利用丰富 context；
- 路线 B：LLM 离线/低频发现规则，快速符号策略在线执行；
- 路线 C：LLM 与 RL/Agent 分层协作。

不能预设哪条一定最好，必须把 latency / cost / adaptation frequency 纳入实验。

# 当前研究的机制坐标

## 候选机制

```text
Context
  = 动态事件
  + 机器/AGV拥堵与瓶颈
  + 搜索阶段
  + Pareto停滞/多样性
  + 上一步策略效果
  + 历史策略轨迹
  + 剩余真实解码预算
        ↓
LLM Contextual Selector
        ↓
固定策略/算子库
        ↓
固定 NSGA-II + 原 decoder
        ↓
Makespan / TEC / HV / decode count / strategy effect
        ↓
历史反馈进入下一轮 Context
```

## 与 HeurAgenix 的区别必须落在机制字段，不落在名字

| 字段 | HeurAgenix 已覆盖 | 当前研究候选差异 |
|---|---|---|
| State | problem/current solution state | 动态调度 + 搜索过程 + Pareto 状态 |
| History | 在线求解状态演进 | 显式策略效果/搜索轨迹记忆 |
| Action | heuristic pool 中 heuristic | 固定优化器的 strategy/operator |
| Executor | problem-solving heuristic framework | 固定 NSGA-II + FJSP-AGV decoder |
| Objective | COP solution quality | makespan + TEC + HV + budget |
| Comparator | 多种 HH/LLM baseline | 对 Q-learning 做单模块同预算替换 |

这些差异目前属于【分析判断】，仍需要进一步核验最新直接文献。

# 机制升级的总链

```text
Human rule
→ Algorithm Selection / HH / AOS
→ RL / Q-learning selector
→ LLM direct optimizer
→ LLM + solver/verifier
→ LLM heuristic generator
→ reflective/evolutionary LHH
→ trajectory / uncertainty / memory-aware AHD
→ heuristic portfolio / multi-operator co-design
→ LLM contextual selector
→ dynamic, multi-objective, feedback-rich supervisory control
```

---

# 当前最关键的研究检验

【分析判断】真正有价值的实验不是证明“LLM 能选策略”，而是拆解它的上下文能力是否真的有用：

1. **C0**：仅动态事件状态；
2. **C1**：C0 + 搜索阶段；
3. **C2**：C1 + Pareto 停滞/多样性；
4. **C3**：C2 + 历史策略效果；
5. **C4**：C3 + 剩余预算。

与 Fixed / Random / Rule / Q-learning / LLM selector 在同一 strategy library、同一 decoder、同一真实 evaluation budget 下比较。

如果 C3/C4 没有稳定提升，就说明“丰富上下文”只是漂亮 prompt，不是有效机制。这个反证也必须允许出现。
