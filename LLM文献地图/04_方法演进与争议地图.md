# 04｜方法演进与争议地图

# 一、方法演进不是“LLM 突然出现”

## 阶段 1｜人工 heuristic / 固定 operator

**解决**：用领域知识把 NP-hard 调度问题变成可计算的启发式搜索。

**留下的问题**：策略依赖专家；一个 heuristic 很难在不同实例、搜索阶段、动态事件下持续占优。

↓

## 阶段 2｜Selection Hyper-Heuristic / Algorithm Selection

**变化的模块**：不再只问“怎样设计一个 heuristic”，而开始问“当前应该选择哪个 heuristic/algorithm”。

**价值**：把“低层求解”和“高层选择”分离。

**代价**：需要设计选择机制、状态/特征、credit assignment 与 move acceptance。

↓

## 阶段 3｜Adaptive Operator Selection

**变化**：选择依据从固定规则进一步变成搜索过程中持续更新的 operator performance / problem state。

**价值**：适应搜索阶段变化。

**问题**：credit 怎么分？短期 improvement 是否代表长期价值？operator sequence 是否存在互补/冲突？

↓

## 阶段 4｜RL / Q-learning 高层 selector

**变化**：把高层选择形式化为 state → action → reward → policy/value learning。

**在调度中的直接证据**：Q-learning HH 已用于带运输资源的 distributed FJSP，并用于动态 robust rescheduling、多目标能耗 FJSP。

**解决**：让 LLH selection 能从交互经验中自适应。

**留下的问题**：
- state definition 高度人工；
- reward definition 影响巨大；
- 状态离散化/泛化困难；
- 新场景可能需要重新训练或调参；
- 可解释性有限。

↓

## 阶段 5｜LLM-driven heuristic / algorithm design

代表路线：EoH、LLaMEA、AHD、E2OC 等。

**变化**：利用语言模型的代码生成与语义推理能力，自动生成/改进 heuristic、operator、solver。

**解决**：降低人工 heuristic design 成本，扩大可搜索的算法设计空间。

**留下的问题**：
- 大量工作偏离线设计，而不是运行时 selection；
- LLM 调用成本和评估成本高；
- 生成代码需要 validity checking；
- 不能自动证明在线实时性。

↓

## 阶段 6｜结构化状态、solver dynamics 与 LLM + RL

TPET：raw numerical state → structured semantic state；LLM 负责发现轻量 policy，而非高频 online actor。

DASH：endpoint score → convergence trajectory / runtime / profile-aware adaptation。

LLM4A3C：不是替换 RL，而是让 LLM 动态调整 state/reward definition。

**意义**：研究焦点开始从“LLM 能不能生成算法”转向“LLM 应该看到什么、控制什么、何时调用、如何与传统学习/优化模块分工”。

↓

## 本研究候选位置｜Context-aware LLM Selection Hyper-Heuristic

**拟改变模块**：只替换高层 selector。

`Q-learning selector → LLM contextual selector`

底层策略库、优化器、解码器和预算尽量保持一致。

这一步目前是研究假设，不是已经由现有文献证明的自然终点。

# 二、争议地图 v0.1

| 争议问题 | 路线 A | 路线 B | 当前证据 | 关键假设 | 当前判断 |
|---|---|---|---|---|---|
| LLM 应在线决策还是离线设计？ | Online LLM actor/selector | LLM 离线生成轻量 policy/heuristic | TPET 明确批评 online actor 的 latency，并选择 discoverer 路线 | 在线调用频率、模型延迟、决策粒度 | **未定**。本课题若在线调用，必须把成本/延迟列为实验变量 |
| 应替代 RL 还是增强 RL？ | LLM 替代 Q-learning selector | LLM 改善 RL state/reward/policy | LLM4A3C 支持增强 RL 路线 | LLM 语义能力能否抵消额外成本；RL 是否已足够学习状态-动作映射 | **证据不足**。必须做竞争设计，而非默认替代更优 |
| 固定策略库还是让 LLM 生成新策略？ | selection HH | generation/AHD | HH 理论与大量 LLM-AHD 分别支持两条路线 | 固定库是否已包含足够多样的有效策略 | 当前小论文更适合固定库，实验变量更干净 |
| 搜索状态是否值得进入 selector？ | 只看环境/实例状态 | 同时看 convergence/stagnation/budget/history | DASH 强化 trajectory-aware 观点；AOS 研究支持 problem state | 状态是否真的有预测下一策略收益的能力 | **值得验证，不应预设有效** |
| 多 operator 是否可以独立评价？ | 独立 credit | 显式考虑 sequence/coupling | E2OC 与 RL-AOS 都指出 interaction/sequence 重要 | 当前策略库是否存在强耦合 | 不能假定独立；需要记录策略转移效果 |
| 最终目标值是否足够评价 selector？ | 只看 final HV/makespan/TEC | 同时看 trajectory、budget、runtime/cost | DASH 直接挑战 endpoint-only evaluation | 研究目标是否包含实时性/效率 | 本课题至少应同时报告质量与计算/调用成本 |

# 三、最容易写错的三条“伪演进”

## 错误 1
`Q-learning 落后 → LLM 更先进 → 所以替换`

错误原因：技术发布时间不是性能证据。LLM4A3C 甚至提供了“保留 RL、LLM 增强 RL”的竞争路线。

## 错误 2
`E2OC 做多算子 → 本研究做算子选择 → E2OC 直接支持`

错误原因：co-design 与 online selection 是两个问题。E2OC 是 A 级机制支撑，不是直接竞争者。

## 错误 3
`DASH 使用 trajectory → 本研究的所有搜索状态都有理论依据`

错误原因：DASH 支持“轨迹信息可能有价值”，不等于证明 AGV 拥堵、Pareto 停滞、上一步改善等每个具体 feature 都有效。具体 feature 仍需消融。

# 四、每 10 篇核心文献后的争议审计

重新检查：
1. 数据集/benchmark 是否可比？
2. 真实解码次数和计算预算是否公平？
3. LLM token/API latency 是否被忽略？
4. 是否只报告最优结果而缺独立重复？
5. 是否有 Wilcoxon/Friedman 等统计检验？
6. 不同论文所谓 state、operator、heuristic 是否其实不是同一层级？
7. 是否把“生成策略”偷换成“选择策略”？
8. 是否把静态 FJSP 结果外推到 dynamic FJSP-AGV？
