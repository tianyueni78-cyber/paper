# 05｜研究缺口与竞争方法地图

# 一、先排除不能当创新点的东西

以下命题当前不能安全使用：

- “首次将 LLM 用于 FJSP” → 已不成立。
- “首次将 LLM 用于动态调度” → 高风险，需系统检索才能判断。
- “动态环境中 Q-learning 没有人做” → 已不成立。
- “多目标 Makespan + TEC + Q-learning HH 很少” → 已有直接研究，不能凭感觉写。
- “LLM 能理解上下文，所以一定比 Q-learning 好” → 没有证据。
- “E2OC 证明 LLM 能在线选择 operator” → 证据越界。

---

# 二、Gap 四级审计

## Gap 1｜对象缺口：FJSP-AGV + LLM

**候选表述**：LLM 在 FJSP-AGV 联合调度中的研究相对有限。

**问题**：即使成立，也只是“对象换了”。创新强度弱。

**当前评级**：低优先级。

## Gap 2｜场景缺口：动态 FJSP-AGV

**候选表述**：现有 LLM-FJSP 方法未必覆盖机器故障/任务到达/AGV拥堵等联合动态事件。

**问题**：需要系统检索，而且“换动态场景”仍不足以单独支撑算法创新。

**当前评级**：中低。

## Gap 3｜机制缺口：LLM 作为固定策略库 selector

**候选表述**：现有 LLM4AHD 主要集中在 heuristic/operator generation、co-design、solver adaptation 或 policy evolution；当前仍需核验是否已有工作把 LLM 明确置于 selection hyper-heuristic 的高层，从预定义 LLH/operator pool 中根据动态环境与搜索状态在线选择策略。

**为什么可能有价值**：
- 保留成熟底层优化器；
- 不要求 LLM 每次重新生成代码；
- 可与 Q-learning selector 做模块级公平替换；
- 可以研究语言语义上下文是否带来传统离散 state 难以表达的泛化能力。

**风险**：一旦检索到高度同构方法，gap 会缩小。

**当前评级**：最高优先级，但标记【待系统检索确认】。

## Gap 4｜能力缺口：状态表达、跨情景适应与成本

### 4A 状态表达
Q-learning selector 依赖人工 state/reward 定义；LLM4A3C 本身已经把“动态调整 state/reward”当作研究问题。

候选问题：结构化语义上下文能否减少脆弱的离散状态设计？

### 4B 动态适应
候选问题：面对未见动态事件组合或不同瓶颈状态，LLM selector 是否比固定 Q-table 更容易迁移？

### 4C 可解释性
候选问题：LLM 输出策略选择理由是否能提供可审计决策依据？

注意：自然语言理由 ≠ 真实因果解释，不能把“会说理由”自动写成可解释性优势。

### 4D 实时性与成本
TPET 直接提醒：online LLM actor 可能存在 prohibitive latency。

因此本研究必须反过来问：

> 即使 LLM 提高 HV，它增加的推理延迟/token/API 成本是否值得？

**当前评级**：高。能力 gap 比“对象没人做”更有论文价值。

# 三、竞争方法地图

| 竞争路线 | 高层机制 | 优势 | 主要风险 | 本研究如何公平比较 |
|---|---|---|---|---|
| Fixed best strategy | 固定使用单一强策略 | 极低成本、稳定 | 无自适应 | 必须保留，防止复杂 selector 实际没价值 |
| Random selector | 随机选择 LLH | 最弱无学习基线 | 性能低 | 检验“选择机制”本身是否有贡献 |
| Rule-based selector | 人工 if/then | 可解释、低延迟 | 规则泛化差 | 使用相同 context 信息 |
| Credit/probability AOS | 历史效果更新概率 | 轻量 | 状态表达有限 | 相同 LLH pool、相同预算 |
| Q-learning HH | state-action-reward | 成熟、低在线成本 | state/reward 设计、泛化 | **核心 baseline** |
| LLM-enhanced RL | LLM 改 state/reward 或辅助 RL | 保留学习能力 + 语义能力 | 系统复杂、训练/调用成本 | 作为强替代路线，至少讨论，资源允许则实验 |
| LLM heuristic generation | LLM 生成新 heuristic | 策略空间开放 | validity/evaluation 成本 | 与当前 fixed-pool selection 不同，不应硬做同类 baseline |
| LLM contextual selector | 结构化 context → 选择固定策略 | 无需训练 Q-table；可能利用丰富语义 | latency、稳定性、prompt sensitivity | 本研究候选方法 |

# 四、当前最值得验证的研究问题

## RQ1｜性能
在相同底层优化器、策略库和真实解码预算下，LLM selector 是否能提高 HV / Makespan / TEC？

## RQ2｜适应性
优势是否集中出现在特定动态事件、瓶颈类型、搜索阶段或停滞状态？

## RQ3｜机制
哪些上下文真正有用？

候选消融：
- dynamic event only
- search state only
- history only
- event + search state
- full context

## RQ4｜成本
质量提升是否足以覆盖 LLM 推理时间、token/API 成本？

## RQ5｜泛化
换实例规模、事件强度或瓶颈结构后，LLM selector 与 Q-learning selector 谁退化得更少？

# 五、当前创新假设

> **【研究假设，不是结论】** 如果使用结构化动态环境状态、搜索轨迹和历史策略反馈作为上下文，让 LLM 从固定低层策略库中承担高层选择，在保持底层 NSGA-II、解码器、策略库与求解预算一致的条件下，相比 Q-learning selector，可能改善动态多目标 FJSP-AGV 中的策略适应性和解集质量；这种潜在收益必须同时接受推理成本、延迟、稳定性与泛化实验的检验。

---

# 六、什么证据会推翻当前首选方向？

1. 找到高度同构的 LLM selection hyper-heuristic + dynamic FJSP 工作，且机制已覆盖本方案。
2. 预实验显示 LLM selector 与 fixed/Q-learning 没有稳定差异。
3. 性能提升来自新增策略库或额外预算，而不是 selector。
4. LLM 调用延迟远大于动态调度允许的响应窗口。
5. prompt/model 改动导致选择结果高度不稳定。
6. LLM-enhanced RL 在同预算下明显优于纯 LLM selector。

如果出现这些证据，应修改机制，而不是继续为“LLM 替 Q-learning”找支持材料。
